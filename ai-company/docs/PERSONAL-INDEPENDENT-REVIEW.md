### 수정이 필요한 확인된 결함

1. **P1 — 후속 수정 업무가 이전 산출물을 작업 기반으로 보존하지 않는다.** `personal-api.mjs`의 `reviewResult()`는 새 작업을 만들지만 `prepareWorkspace()`는 다시 프로젝트 원본 저장소를 복제한다. 이전 결과가 아직 원본에 병합되지 않은 일반적인 검토 흐름에서는, 그 결과를 수정 요청하자 새 작업 폴더에서 기존 변경 파일이 사라졌다. 임시 실제 Git 저장소에 `accepted-feature.txt`를 추가한 검토 브랜치를 만든 뒤 수정 요청→새 작업 공간 준비를 실행했으며 `parentChangedFilePreservedInRework=false`를 확인했다. 부모 결과의 정확한 commit과 프로젝트 범위를 확인한 뒤 후속 작업 기준으로 보존해야 한다.

2. **P1 — 오래된 결정 답변이 취소된 업무를 되살린다.** `decisionInbox()`는 pending 결정만 확인하며 연결 업무의 현재 상태를 확인하지 않는다. `resolveDecisionGroup()`는 그 결정에 답변하면 무조건 queued로 바꾼다. 정보 대기 결정 생성→업무 취소→남아 있는 결정에 답변 순서에서 `cancelledTaskAfterStaleDecision=queued`를 확인했다. 현재 단계와 상태에 유효한 결정만 응답 대상으로 삼고, 종료 상태를 재실행하지 않아야 한다. 기존 단건 결정 API도 같은 경계로 확인할 필요가 있다.

3. **P2 — 대표의 회의 후속 메시지가 참석 직원에게 전달되지 않는다.** `src/main.tsx`의 회의 전송은 recipient 없이 channel만 `/messages`에 보낸다. API는 메시지를 저장하지만 회의 작업/수신자/실행을 연결하지 않는다. 초기 안건에 대한 직원 응답이 끝난 뒤 대표가 질문을 남겨도 직원이 받는 작업이 생기지 않는다. 열린 회의의 참여 범위 안에서 후속 입력을 연결하고, 중지·종료된 회의에서는 호출이 발생하지 않는 검증이 필요하다.

4. **P1 — 기존 단건 결정 API가 정보 답변을 범위 승인으로 승격한다.** `server/app.mjs`의 `/decisions/:id/resolve`는 정보 결정에도 `scopeApproved:true`를 기록한다. 새 정보 대기 결정은 기존 자율 운영 화면에도 노출되므로 새 개인 결정함의 안전한 분기만으로 해결되지 않는다. 독립 HTTP 탐침은 허용 범위가 `bugfix`뿐인 프로젝트에서 `feature` 업무의 정보 질문에 답변했고, 응답 `200`, `scopeApprovedAfterInfoAnswer=true`, 모델 호출 `0`을 확인했다. 범위 승인은 `scope` 결정에만 연결하고 단건/그룹 경로를 같은 검증으로 처리해야 한다. 이 권한 경계 결함이 남으면 점수와 무관하게 미통과다.

## 2차 검토의 추가 발견과 수정 재검증

1차의 네 결함은 구현자가 수정했다. 후속 작업은 검토된 부모의 정확한 HEAD에서 복제하며 부모가 dirty이거나 HEAD가 달라지면 중단한다. 상태를 벗어난 결정은 superseded 처리되고 그룹/단건 API 모두 현재 대기 상태를 확인한다. 정보 답변은 범위 승인이 되지 않는다. 대표 회의 후속 메시지는 선택된 참여 직원의 별도 작업으로 이어진다.

추가로 다음 두 상태 결함을 독립 탐침으로 발견해 전달했다.

- 회의의 두 번째 참여자가 프로젝트에서 제거된 경우 HTTP 409 뒤 첫 번째 참여자의 작업이 남았다. 구현자는 모든 수신자를 먼저 검증하고 메시지·작업 저장을 단일 트랜잭션으로 바꿨다.
- PO 질문에 답한 뒤 CTO 단계의 다른 정보 부족이 생기면 PO의 옛 질문이 재사용됐다. 구현자는 대기 상태 탈출·단계 전환 때 현재 요청을 초기화하고, 질문 없는 새 보고도 초기화하도록 바꿨다. 과거 결정 원문은 유지한다.

구현 테스트와 별도로 작성한 임시 Git/HTTP 탐침 5개를 다시 실행했다. 부모 산출물 보존, 취소 업무 재개 차단, 단계 간 질문 재사용 차단, 잘못된 회의 참여자의 부분 저장 차단, 단건 정보 답변의 권한 승격 차단 **5/5 통과**. 이 탐침의 모델 호출은 0이다.

## 3차 검토 대기 — 실제 증거 다운로드 실패

2차 판정 뒤 구현자의 실제 원장 화면 점검에서 증거 다운로드가 HTTP 409 `Not Found`로 실패했다. Express 다운로드의 기본 dotfiles 차단 때문에 `.local` 아래의 정상 증거 파일을 제공하지 못하는 연결 결함이다. 실제 모델 결과와 파일 자체의 검증 성공을 사용자가 앱에서 증거를 다운로드할 수 있다는 검증으로 대신했던 공백을 기록한다.

**회사 앱의 2차 98점 통과 판정은 보류한다.** 구현자가 범위가 검증된 실제 파일 경로에만 숨김 경로 다운로드를 허용한 뒤, 독립 재검증으로 새 판정을 남겨야 한다. 기존 모델 실행·결과·실패 기록은 보존하며 이 확인을 위해 모델을 추가 실행하지 않는다. LessonQuest 코드 자체의 95점 좁은 범위 판정과 실제 계약 테스트 근거는 이 UI/API 다운로드 결함과 구분한다.
