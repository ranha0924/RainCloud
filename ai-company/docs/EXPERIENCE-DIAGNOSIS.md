# A/B/C 동점 진단 · 2026-09-10

추가 모델 호출 0회. 기본 회사와 실증 데이터의 `settings.stopped=true`를 저장하고 앱 실행기를 종료했다. 기존 회사 1,000,000토큰/100턴, 실증 프로젝트 350,000토큰/50턴, 전이 프로젝트 140,000토큰/24턴 및 각 평가의 고정 한도는 유지했다. 이전 자율 운영 프로젝트의 500,000토큰 한도도 그대로다.

## 짧은 판단

- **확인된 사실:** 완료한 `auth-08`의 C에 활성 공유 지침 1개(v2)가 실제 App Server 입력으로 전달됐다. 원본 경험은 0개다. C는 동일 시각 만료와 `now` 누락을 재현했지만, 저장된 채점은 둘을 한 계약 결함으로 합쳤다. A/B도 한 결함을 찾아 발견/놓침/오지적은 모두 1/0/0이었다.
- **가능한 원인:** 명시적인 짧은 계약과 한 결함 단위의 점수에서 A/B가 이미 상한에 도달했다. C의 내용은 관련 있었으나 기본 계약과 일반 체크리스트를 구체화한 두 점검 문구였다. 추가 입력·보고 비용도 있었다. 어느 요소가 결과를 일으켰는지는 단일 실행으로 분리할 수 없다.
- **아직 모르는 것:** 반복 실행 변동, 실제 서비스에서의 효과, 사람이 검수·수정하는 시간, 금액, 모델이 해당 지침 때문에 행동을 바꿨는지는 확인 불가다. 기록된 입력 전달과 모델의 적용 자기 보고는 인과 효과의 증거가 아니다.
- **다음에 필요한 최소 검증:** 모델 호출 전에 결함 유형/재현 범위의 판정 기준을 새 버전으로 고정하고, 정상 1개와 독립적인 결함 사례 1개를 선정한다. 회사 잔여 한도 안에서 A/B/C 각각 같은 토큰 예산을 확보할 수 있는지 확인한다. 확보되지 않으면 실행하지 않는다. 이번 진단에서는 새 평가를 만들거나 실행하지 않았다.

## 실제 입력 대조

근거는 회사 SQLite의 고정 조건·run·events·지침/허가 기록과 해당 thread ID의 Codex rollout JSONL이다. DB는 읽기 전용으로 조회했고, 다른 대화는 읽지 않았다. 원본 응답·산출물·고정 조건·점수를 수정하지 않았다.

완료 비교: `93661ada-7dac-43a9-831f-92ee330384ff`, `auth-08`, `gpt-5.6-luna`, reasoning `low`.

각각 다른 thread ID/작업 폴더를 사용했다. 코드·공개 계약의 해시는 모두 `27bfaba491f214f0e82b683ae05935d7f4317d32bddf2a3a5aae5543ae384e9f`이고, 두 동적 도구 정의의 실제 해시는 고정 값 `0364d8398f6beab300f2a758b537f90b8e2c74889e9d8134a32c34b0ccac22d4`와 일치했다. 세 조건 모두 read-only이며 각 75초/도구 20회/앱 턴 1회다. 평가 전체 토큰 한도는 140,000이었다. 토큰 한도는 조건별 독립 예약 방식이 아니었다.

A/B의 사용자 입력은 동일하다. C에는 선택된 지침 ID·활용 설명·충돌 이유를 보고하라는 문장이 추가됐다. C에 보고 부담이 더 있으므로 실행 시간·출력 토큰의 차이를 순수한 검색 효과로 볼 수 없다.

- 원본 프로젝트: `QA 경험 실증 · 연습과 평가` (`54d8d6dc-d229-4046-ad67-60a10fe1169b`).
- 근거 경험: `run:a35308c4-ecc1-47cc-982c-f1432263f1ec`, `practice-refresh-01`, **연습**, 실제 함수 실행 및 고정 oracle 검증. 실제 업무나 대표의 사람 평가로 집계하지 않는다.
- 피드백: `03578650-edd4-42d7-8933-1afceb053d2c`, 작성자 `implementation_validation`.
- 지침: `f09e0bed-2202-4044-868e-8b2c8c169214` v2, 검증됨/활성. 검토 감사 기록 시각 `2026-09-10T04:05:47.829Z`.

- 공유 로직은 원본 6단계 서술/산출물/코드를 옮기지 않고, 허용된 `expiry`와 `fail_closed`의 고정 일반 문구만 구성했다. 따라서 이 비교는 풍부한 원본 경험 검색의 효과보다 **경험을 근거로 허용한 구체적 점검 문구 추가**에 가까운 조건이다.

당시 DB의 `instructionSnapshot`에는 공통 Windows 안내 224자가 빠져 있었다. 그 접두부는 rollout 메시지와 일치하며 실제 전달된 전체 내용은 rollout으로 확인했다. 현재 runtime은 Windows 안내를 합친 뒤 스냅샷과 해시를 저장하도록 앞선 구현에서 수정되어 있다. 이번에 과거 스냅샷을 덮어쓰지 않았다. 제공자에게 전송된 최종 직렬화 요청이나 모델 내부 주의 배분은 이 로그만으로 확인할 수 없다.

부분 실행의 `auth-02 C`도 지침 1개와 **같은 프로젝트의 연습 경험 1개**가 실제 입력에 포함됐다. 두 `auth-01` 파일럿의 C는 실행 자체가 없어 선택된 자료는 고정 조건으로만 확인되며 실제 모델 전달은 확인할 수 없다.

## 관련성·중복·채점 상한

B의 네 문구는 정상/거절 입력 비교, 실제/기대 결과 불일치 확인, 동일 원인 중복 제거, 개발자 보고와 별개인 실물 확인이다. C의 추가 문구는 다음 두 가지다.

1. 세션 유효 시간의 직전·동일 시각·직후 경계를 각각 재현한다.
2. 필수 인증 정보가 없거나 유효하지 않으면 접근이 거절되는지 확인한다.

**문장 완전 일치 기준으로는 추가 2개 중 B와 같은 문장 0개**다. 의미상으로는 둘 다 B의 정상/거절 입력 비교를 구체화한다. 의미 중복률을 수치로 측정하지 않았으며 임의의 유사도 백분율을 제시하지 않는다. 이번 과제의 세션 만료·누락 문제와는 직접 관련 있다.

공개 계약은 `authenticated=true`, 정수 `expires`, `now < expires`일 때만 허용한다. 실제 코드는 `!(now > expires)`를 사용한다. 동일 시각과 `now` 누락 모두 true가 나와 계약과 불일치한다. A는 동일 시각, B도 동일 시각, C는 동일 시각과 now 누락을 보고했다. B는 expires 누락도 실행했지만 이 입력은 정상 거절됐고 결함으로 보고하지 않았다.

저장된 정답/판정의 단위는 `auth-08:contract` 한 개다. `judge()`는 재현된 다른 입력도 같은 `defectId` 집합에 넣는다. 따라서 A/B가 1개를 찾은 시점에 발견 수 상한에 도달했고, C의 추가 입력은 발견 수를 높일 수 없었다. 저장된 결과는 다음과 같다.

| 지표 | A | B | C |
|---|---:|---:|---:|
| 확인 결함 / 놓침 / 오지적 | 1 / 0 / 0 | 1 / 0 / 0 | 1 / 0 / 0 |
| 확인된 재현 입력 / 보고 | 1 / 1 | 1 / 1 | 2 / 2 |
| 재현 정확성 비율 | 1.0 | 1.0 | 1.0 |
| 토큰 | 28,374 | 28,717 | 30,006 |
| 경과 시간(초) | 15.837 | 25.377 | 21.757 |

재현 정확성은 입력을 함수에 다시 넣어 기대값과 비교한 값이며, 자연어 재현 절차를 사람이 검수한 점수가 아니다. 추가 재현 입력 수는 관찰됐지만 독립 결함 증가나 사람 작업 시간 감소로 바꾸어 해석할 수 없다. C는 두 건으로 표현했고 자동 판정이 하나로 정규화했다.

현재 oracle 함수/정답 witness의 해시는 저장된 `answerHash`와 일치한다. **채점 함수 전체 코드의 당시 스냅샷/해시는 저장하지 않았으므로 당시 판정기 전체를 독립적으로 복원할 수 있는 수준은 아니다.** 기존 점수는 보존하고, 다음 평가에서는 이 부분도 고정해야 한다. 과거 점수를 C에 유리하게 다시 나누지 않았다.

## 확인한 구현 문제와 수정

1. `retrieveExperience()`가 `evaluationId !== excludeEvaluationId`를 무조건 검사했다. 둘 다 undefined인 실제 업무 경험은 탈락했다. 제외할 평가 ID가 제공됐을 때만 검사하도록 수정했다. 같은 프로젝트의 검증된 실제 업무를 찾고, 다른 프로젝트에는 원문을 보내지 않는 회귀 테스트로 확인했다. 완료한 전이 C의 원본 경험 0개는 별도 공유 정책 때문이므로 이 버그가 이번 C 입력을 줄였다고 판단하지 않는다.
2. 평가 검색어에 login/session/auth 등을 강제로 추가했고 공개 입력 계약에도 여러 인증 필드가 나열됐다. 이 때문에 expiry 지침이 role 과제에도 선택됐다. 새 평가를 고정할 때 명시적 과제 topic과 지침 checkCodes의 일치를 요구하고 `retrievalVersion=case-topic-1`을 남긴다. 과거 고정 selection/조건 hash에는 반영하지 않는다. 일반 업무의 자유 검색이나 다른 프로젝트 사용 권한을 확장하지 않았다.

두 회귀 테스트가 수정 전 각각 실패함을 확인했고 수정 후 통과했다. `npm run verify`는 **37개 테스트, TypeScript 검사, Vite 빌드 모두 통과**했다. 현재 auth-08은 expiry 지침과 일치하므로 두 번째 수정도 기존 동점의 설명으로 보지 않는다. 이 사례에서 지침 활성화나 실제 입력 전달이 실패한 근거는 발견하지 못했다.

## 근거와 재현

- 읽기 전용 감사 도구: `scripts/audit-experience.mjs`.
- 상세 입력/해시/허가/사용량: `.local/experience-diagnosis/audit.json`. 원본 프로젝트 근거가 포함되므로 프로젝트 간 모델 검색 도구나 공개 API에 연결하지 않는다.
- 원본 회사 DB: `.local/autonomy-live-verified/data/company.sqlite`.
- 원본 결과: 위 데이터의 `evaluation-results/93661ada-7dac-43a9-831f-92ee330384ff/`.

node scripts/audit-experience.mjs --data .local/autonomy-live-verified/data --sessions C:/Users/Raina/.codex/sessions --output .local/experience-diagnosis/audit-after.json
